A gate between your AI agent and your money.

A NEAR smart contract holds the money you set aside for your agent. It pays only for jobs you signed. Any other request is refused: nothing is paid, and the reason is recorded on-chain.

How the gate decides

An AI agent wants to spend your money. Nothing is stamped yet, so the gate refuses.

You stamp (sign) each job it may pay for: recipient, maximum amount, exact instruction.

The agent asks for exactly that job, within your limit: paid.

A different instruction, a fake owner, or a higher amount: refused, and recorded.

Above the review amount you set, a payment waits for your approval.

It sends four preset requests to one test gate from your testnet wallet. Each attaches 0 NEAR and costs a little testnet gas.

Every payment request ends in one of three ways

  • Paid

    Testnet NEAR leaves the gate only for a stamped job.

  • Held

    Above your review amount, the payment waits for your approval. After the deadline (one hour at most) it can no longer be approved, and nothing is paid.

  • Refused

    Nothing is paid. The transaction itself goes through and stores a reason code on-chain, so anyone can check what the agent tried.

Up to three checks, in order

  1. 1

    Contract rules

    Stamped jobs, limits and budgets are checked on-chain.

  2. 2

    Judge model (optional)

    An optional second check: a judge model reviews the request before payment. Used live in testnet Run B (see Proof).

  3. 3

    Your approval

    Payments above your review amount wait for you.

Limits

  • Testnet prototype. Not audited.
  • Not deployed on mainnet. No real funds.
  • The stamp key (the key you sign jobs with) cannot be changed later. Back it up before you deposit.
  • Anyone who knows a mandate serial can freeze it with the same refused request from the same account twice in a row (with no passing request in between), or three mandate-check refusals in a row. Nothing is paid, a new mandate recovers use, and that mandate can be frozen again. The refusal count goes back to 0 only when a request passes the mandate checks with an amount above 0 and the transaction does not fail, whatever follows: a payment, a new hold, a spend-rule refusal (tier2_deny), or an allowed request that pays nothing (an authorize call or an action other than a transfer). A zero-amount request leaves the count unchanged. Approving or rejecting a hold later does not change it.
  • Anyone can grow the gate's storage with refused requests that carry long strings: in the sandbox, 3 requests grew storage by 63,758 bytes, and a full escrow withdrawal then failed with LackBalanceForState, about 0.028 NEAR short. A plain NEAR transfer (not Deposit) of the shortfall fixes it. There is no per-mandate storage cap in the contract (a 4th call on an already frozen mandate added 0 bytes in that run), and the fix is designed, not deployed.

If you lose the stamp key you cannot take the escrow out. It is stored in this browser without encryption.
