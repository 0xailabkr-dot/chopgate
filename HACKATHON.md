# ChopGate — hackathon summary

**ChopGate is a NEAR smart contract (a gate) that holds an owner's funds in escrow. It pays an AI agent's request only when the request matches a job the owner signed, refuses everything else on chain with 0 paid, and holds larger payments until the owner approves. Testnet prototype, not audited.**

## 30-second summary

- **What it blocks:** an AI agent paying with the owner's NEAR when the payment does not match an owner-signed mandate. Instructions outside the mandate, impersonated owners and over-limit amounts are refused on chain. A refusal is a successful transaction: the contract pays nothing and records a reason code.
- **Why it is needed:** an agent that holds a wallet key can be steered by injected text. With ChopGate the agent holds one function-call key for one method on its gate. It cannot send NEAR. It can only ask the gate, and the gate checks the owner's signature on the exact job.
- **Try it:** open the demo at https://0xailabkr-dot.github.io/chopgate/. The first screen shows the idea as a short looping illustration and a five-scene walkthrough. Then go to Proof, connect a NEAR testnet wallet and send the four preset attacks. None is paid.
- **One command:** `./check.sh` → `CHECK: ALL OK`.

## Tracks

- **Security:** refusals on chain with 0 NEAR paid (Runs A to D), owner approval for payments above a review amount, a mandate freeze after repeated refusals by the mandate checks, and four attacks anyone can send from their own testnet wallet (Run C). An owner approval is bound to the hash of the exact request (shown on testnet in [Run G](docs/RUNS.md#run-g)). On testnet, an approval signed by a different key fails. The refusal count goes back to 0 only at `src/lib.rs` line 811, when a request passes the mandate checks with an amount above 0 and the transaction does not fail, whatever follows: a payment, a new hold, a spend-rule refusal (`tier2_deny`), or an allowed request that pays nothing (an `authorize` call or an action other than a transfer). A zero-amount request returns at lines 787-789, before that line, and leaves the count unchanged. A failed payout check at lines 803-808 reverts the whole transaction, so the count is unchanged too. Approving or rejecting a hold later (`resolve_pending`, line 950) does not change it. A spend-rule refusal still uses the job and its share of the budget.
- **Agents:** the agent account holds one function-call key (one method, one gate). On testnet that key could not transfer NEAR, call another contract, call another method of its own gate, or attach a deposit (Run D). A factory creates each gate with 0 access keys (Run E). The owner and agent steps were also done from a browser with a wallet, with the MCP server in `agent/` (Run F).

## Judge model

TypeSafe System One, model `jev-latest` (Run B responses reported `jev-1.14.0`). One yes/no question about the mandate scope. p(yes) is the model's probability of "yes". The judge's own answer is allow at p(yes) ≥ 0.90, human approval from 0.50 up to but not including 0.90, and block below 0.50 (tested locally: `src/jev_live.rs::tests::thresholds_boundaries`); the deterministic rules still decide first, and Run B scene 5 had p(yes) 0.98 and ended `tier2_escalate`. Thresholds are in `config/jev.json`. p(yes) is an off-chain answer copied into the signed judge report, so it appears in the transaction arguments. For scenes 1 and 5 it also appears in the `tier2_decision` event log; scene 4 is refused by the entry limit before tier 2, so it has no such log. The log lines are quoted in the saved RPC check. A judge answer cannot override the mandatory limits (tested locally: `src/jev_live.rs::tests::mandatory_rules_cannot_be_overridden`). Below those limits, a signed judge report can let a payment pass without human approval: in Run B scene 1 a report signed by the registered demo judge key ended `allowed`, while a re-pointed copy with a stale signature escalated (`tier2_escalate`). No key, an error or a timeout → human review. The local checks use an offline mock judge.

## Limitations

Testnet only, not audited, no mainnet deployment. The contract does not verify any TypeSafe signature. A model answer is an opinion, not proof, and nothing on chain proves that a judge call happened. The instruction source is supplied by the caller. `webapp/` is an older local prototype with mock signing; the hosted site in `site/` talks to testnet through a wallet. The wallet list has 6 wallets. Signing in the wallet window was tested with Intear. Meteor was checked up to the mainnet-account notice. Two code changes made after Run B were not re-run on testnet (see the README "Limitations"). Hold expiry was shown once on testnet (Run C). Binding an approval to the exact request hash is shown on testnet in [Run G](docs/RUNS.md#run-g).

A local sandbox run on 2026-11-14 (near-sandbox, contract code hash `8Qtk3jf4RLpfiB7PeXeuPGYcp4USV2yeN5Zn3d5NpAMj`) found two further limits. Anyone who knows a live mandate serial can freeze it for good from their own account: the same refused request from the same account twice in a row (with no passing request in between), or three refusals by the mandate checks in a row. In that run the first call was `wrong_caller` and the second was `auto_frozen`; the agent then also got `auto_frozen`. No NEAR is paid. Recovery is a new mandate with a new serial. The old serial stays frozen, and the attacker can freeze the new one the same way. The refusal count goes back to 0 only at `src/lib.rs` line 811, when a request passes the mandate checks with an amount above 0 and the transaction does not fail, whatever follows: a payment, a new hold, a spend-rule refusal (`tier2_deny`), or an allowed request that pays nothing (an `authorize` call or an action other than a transfer). A zero-amount request returns at lines 787-789, before that line, and leaves the count unchanged. A failed payout check at lines 803-808 reverts the whole transaction, so the count is unchanged too. Approving or rejecting a hold later (`resolve_pending`, line 950) does not change it. A spend-rule refusal still uses up the job and its share of the budget, and nothing is paid. Only refusals by the mandate checks count toward three in a row or the same attempt twice. Anyone can grow the gate's storage with refused requests that carry long action or target strings. Those strings are kept in the refusal record and the event log. In that run, 3 requests with 15,802-character strings grew storage by 63,758 bytes. The contract has no per-mandate storage cap; in that run a 4th call on the already frozen mandate added 0 bytes, but other mandates on the same gate can be used the same way (not tested). After that, withdrawing the full escrow failed with `LackBalanceForState`, about 0.028 NEAR short. Calling `deposit()` does not fix it: it raises escrow by the same amount. A plain NEAR transfer to the gate account (not `deposit()`) of the shortfall fixes it; then the full withdrawal succeeded. In that run the second and third calls added 15,896 bytes each; larger strings were not tested. Fix design, not deployed: calls from anyone other than the mandate's agent would not touch the mandate's counters or storage; stored strings would have a length limit.
